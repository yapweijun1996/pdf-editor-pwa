# Module provenance records

Keep one JSON record per independently authored module or coherent documentation deliverable. Copy [template.json](template.json) to a named record here, replace **all** placeholders (including the example date and zero hashes), and validate against [schema.json](schema.json), JSON Schema Draft-07. The template is shape-valid, not evidence. Records are not signed merely by passing validation.

- `module`: identify the module and scope. `author`: identify the actual author or attributable agent identity and role. `authoredOn`: UTC calendar date of the recorded revision.
- `revision`: record the base Git commit and a map of repo-relative deliverable paths to SHA-256 of raw bytes. The digest map identifies the exact working-tree contents, including untracked files; the base commit alone does not. Exclude the record itself to avoid self-reference. Review the provenance text as well as the hashed deliverables; attach the review to a versioned evidence reference that captures the record inputs and verdict. Do not use placeholders, external paths or symlinks in a live record.
- `sources`: resolve every `sourceId` in the [source ledger](../notes/sources.json) or a versioned extension identified in `notes`. Give specific sections or locators and state what came from each reference. Ledger entries identify documents by version, location and consultation date. Mark inaccessible/unconsulted material as such in a ledger, never as relied-on evidence. Describe independent derivation, assumptions and limitations in `notes`. Fixture artifacts also need the per-file generation and rights information described in the [fixture notes](../notes/phase0-fixtures.md).
- `review`: author leaves `pending` with null reviewer/date/revision and empty evidence. A different engineer checks permitted sources and mappings, contamination history, notes and claims, rights and any applicable verification evidence. Recompute every digest and check complete scope, author/reviewer independence, and date ordering. The reviewer alone records `approved` or `changes_requested`, their identity/role, date, the exact `reviewedRevision` (same base and digest map), evidence references and findings. Evidence can be a versioned review report or a tracked review reference with conclusions and the artifact fingerprint, not just a status label. Identify every contributor in notes if needed; none may sign the review.
- Reopen review on changes to the module, substantive provenance claims or relevant evidence; preserve past decisions in versioned history, and do not reuse approval. Missing/inconsistent evidence leaves the gate open. Schema checks cannot prove identity, independence, truth of sources, or byte-level revision equality; check those separately. Enable calendar-date format checks when validating. Provenance approval does not sign off QA, security, release licensing or similarity review.
