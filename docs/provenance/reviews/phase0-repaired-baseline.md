## Blocking finding

The repaired harness rejects opaque white on marked pages, but can still report a match when two navigation stages display stale content. `observeRender` rejects the exact preceding bitmap only when the expected reference changes. A nonadjacent cached bitmap survives that guard; similar page layouts can then pass the grid checks even though the correct page was never visible.

I reproduced this in Chromium 159.0.8154.6 on unchanged `PER-01` (50 pages), with a review-only injection that replays raw `ImageData` on the visible main canvas after the real draw. It did not fake reads, UI page numbers, backing-store resets, or reader references. Replaying page 1 at page 25 (directly preceding) was correctly rejected. Replaying page 1 at page 50 after a successful page 25 incorrectly passed the last-page stage; the following normal return to page 1 was rejected as a repeat. In a third run, replaying page 1 at page 50 and page 25 on return to page 1 made **both** navigation stages pass and the entire row report `match`. Observed downsampled pixel SHA-256 values matched the earlier real page 1 and 25 observations exactly. The three Poppler reference digests were distinct. The wrong page 50 observation scored 0.977 recall / 0.989 precision; the wrong return scored 0.981 / 0.907, comfortably over 0.72 / 0.50. The unchanged app was not observed to do this without injection.

The manager should route the harness back to a repair author. Require a real-browser regression for nonadjacent cached pages as well as the original white and blank controls, and require page-discriminating evidence for any navigation timing counted as successful. Preserve legitimate returns to earlier pages and genuine identical rasters. Do not use this injected result to change the recorded natural app outcomes.
