# Clean-room policy

Applies to independently authored PDF modules, fixture recipes, generated corpus artifacts and measurement tooling. [ENGINE-PLAN.md](../ENGINE-PLAN.md) sets the licensing, independence and release gates. This Phase 0 workflow deliberately excludes implementation-source access even where the plan separately permits investigating a permissively licensed dependency bug. That exception is not a route into clean-room work.

## Inputs and handoff

- Derive behavior from public specification text and permitted public documentation or standards. Record edition, URL, section or other locator, access date, and how the source informs the work. Treat examples as references, not material to paste. Public access does not grant redistribution rights. Only paraphrase the behavior needed here; do not import spec examples or PDFs into the corpus.
- Do not inspect existing PDF engine code or tests, dependency sources, `vendor/`, PDF packages under `node_modules`, decompiled output, source maps, or implementation excerpts from docs, search results, issue threads or AI suggestions. No implementation copying, including permissively licensed code, into our modules. Do not ask a tool or another person to summarize internals for authors.
- Research hands off independently written behavior notes, source references, fixture expectations and limitations. Implementers design from those inputs and record their own sources. If forbidden material is encountered, stop work on the affected module, quarantine the tainted notes without forwarding excerpts, record the exposure and affected scope, and route to an independent reviewer for reassignment or independent re-derivation. Do not silently self-clear.
- Oracle use is black-box only: run a pinned installed reader or validator through documented public UI/CLI interfaces on synthetic files. Record version, settings, input hash and sanitized observations (open status, counts, visible features, check diagnostics). No source reads, tracing internals, memory dumps, debugger inspection or code-bearing logs. Keep files local. The specification and fixture recipe define expected behavior; differences between tools are findings, not new requirements. Do not use oracle output PDFs as source fixtures or use the app's own renderer as its second reader.

## Licensing and provenance gates

- A dependency is not our implementation. For bundled dependencies use only allowed MIT, Apache-2.0, BSD-2/3-Clause or ISC material with verified license and origin, include license and notices, and list in `THIRD-PARTY-NOTICES`. Keep dependencies unmodified where possible and document patches. Do not admit incompatible/copyleft material as specified in the plan, source-available or non-commercial material, unlicensed files or unknown licenses. Runtime access does not authorize source access.
- Generate fixtures independently, including their text, art, samples and ancillary inputs. Record artifact hashes, generation recipe, inputs and rights-holder CC0-1.0 dedication; a license label alone is not a dedication. No downloaded PDF specimens. Do not dedicate material we do not control.
- Keep a [provenance record](provenance/README.md) per authored module. An independent engineer reviews the exact recorded revision. Authors do not sign their own provenance, QA or security gates. Before each release, a reviewer who did not introduce the dependency audits each bundled file's name, version, license, origin, retained notices and any patches; provenance and similarity checks do not substitute for this audit. QA retains blocker/minor/cosmetic classifications; only blockers fail a QA round.

## Mechanical similarity review (no third-party source disclosure)

1. A non-author review operator pins the candidate revision, authored code file list, bundled comparator inventory (versions and digests), comparator tool/version and settings. The operator grants read-only access to an isolated, local comparator process, not to researchers, implementers or reviewers. No uploads, source browsing or interactive side-by-side diff. This is a separate release workflow, not a Phase 0 research action.
2. Compare exact file hashes and mechanically compare token windows or fingerprints for near matches. Record tokenizer/normalization, window size and alert threshold before scanning; do not report a skipped language or unreadable file as clear. Verify coverage and positive/negative controls using synthetic examples. Keep source-bearing intermediates and tool stderr quarantined; disable snippets, raw tokens, stack traces and source-bearing output before the run. If tool output cannot be safely filtered, stop and report blocked.
3. Export only an allowlisted summary: revision, tool/setup, inventories or their IDs/digests, coverage, counts, match IDs, authored paths/ranges, opaque comparator IDs and scores, omissions and verdict. No third-party snippets or reversible fingerprints. A reviewer checks matches using only authored material and documented spec constraints or boilerplate; log the disposition by match ID. Unresolved material similarity or incomplete coverage blocks clearance. If needed, commission an independent rewrite from recorded allowed inputs, then rerun. A clear report is evidence, not proof of independent authorship.
4. Retain the sanitized report along with the provenance and license-audit evidence. No author clearance, no rubber-stamping absent evidence, and no carry-over across changed inputs. This policy defines the protocol; it does not claim a scan or approval occurred.
