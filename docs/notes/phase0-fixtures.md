# Phase 0: fixture and baseline measurement notes

Goal `97e94b6a-60de-44e6-89d0-3b785f0b3a95`. Generate a corpus from scratch and measure the **current, unchanged app**. This is not a design for a new parser, a product QA run, or evidence for the production ≥95% corpus-open gate. These are recipes and measurement instructions, not generated files or observed results. The recipe matrix and measurement method retain the original Phase 0 design. The stricter source-access workflow used for the original research is historical; the current [license and provenance policy](../CLEAN-ROOM.md) permits reading permissively licensed dependency source for understanding, debugging and audit, but not copying, translating or porting it into our modules.

**Planning assumption:** `ENGINE-PLAN.md` sets feature areas and gates but no numeric category allocation. The 150-file distribution below is a proposed test design, not an official acceptance matrix. Count each input exactly once by primary category; use secondary tags for overlap. Outputs, logs, control re-runs and derived save copies do not count. All PDF section numbers refer to [ISO 32000-1:2008 as published by Adobe](sources.json), not ISO 32000-2. `open` means a standards-valid input is expected to display its intended page(s) as a baseline target; it is not a claim of app support. Report differences rather than excluding difficult inputs.

## Generator and manifest handoff

- Generate byte-accurate files: maintain canonical serialization, deterministic seeds and dates, explicit PDF version/feature compatibility, and byte-checked object offsets, stream lengths and revision links. Use simple independent layouts first, then paired variants with one changed axis. For negatives, record the specific violated rule and parent case ID/hash (or document why there is no parent). Restrict malformed cases to benign small inputs. Validate positive cases with a pinned independent public-interface oracle; resolve disagreement or mark unverified, never copy its output to fix fixtures.
- Suggested build order: baseline → table/stream/object/revision variants → geometry/rendering/forms/metadata → encryption, negative and performance sets. First verify one sample of each recipe group, then expand to the assigned counts. Independently authored glyphs, swatches, rasters, strings and XML are preferred; no third-party asset payloads. If a required format or profile needs another public standard, record it before relying on it, or document a conforming substitute within the same category. Do not silently replace or drop deferred cases.
- Future manifest: record corpus version; per PDF record ID, relative path, primary category, secondary tags, declared version, byte length and SHA-256, standards validity, expected outcome, intended page count/order and markers or exact reason not applicable, fixture-specific preservation checks and negative mutation or encryption profile if relevant. Separate recipe expectations from oracle and app observations. Freeze the manifest and inputs before runs and reject duplicate IDs, path escapes, count mismatches and missing hashes.
- Future artifact source/license ledger: per PDF and any included/generated input asset, record ID/path/hash, origin (`self-generated`), recipe ID and generator version/commit, parameters/seed, parent and constituent input IDs/hashes (empty array for none), source ledger IDs and sections, author identity/role and generation date. Link the rights holder's explicit CC0-1.0 dedication to the identified output scope, date and version; record the legal-code URL. Give recipe/generator code its own provenance and applicable license record. A third-party file, bundled font program, standard PDF or undocumented origin does not qualify. The [research source ledger](sources.json) is not an artifact ledger. For the implemented corpus, see the [manifest](../../tests/corpus/manifest.json) and its separately scoped [dedication](../../tests/corpus/CC0.md).

## Baseline harness handoff

1. Run the exact current app revision without changes, using the publicly observable picker/UI, render output and download events. Start from a known app-ready state; record cold and warm runs distinctly and identify app cache state, not just browser startup. Run locally with synthetic data only; after local setup record network conditions and observe requests for unexpected document egress. Apply the [black-box measurement protocol](../CLEAN-ROOM.md#black-box-measurement-protocol): pin a second independent reader and optionally a structural checker. Record exact version/settings; no imports of private APIs, inspection of implementation internals as part of the measurement, or source-bearing output.
2. For every case, record expected category and independently observed app outcome: `opened`, `password_error`, `corrupt_error`, other error, partial render, timed out, crashed, skipped, or unavailable (with reason). Capture visible error class/text and whether subsequent known-good open works after a negative. `opened` requires first expected visible content (or intentional blank plus page-ready evidence) and expected page count; record later render/feature failures separately. Report raw counts by category, unscanned cases, valid-unencrypted open fraction (denominator 130; retain skips/timeouts separately), and whole-corpus open count out of 150 with expected negatives separated. Do not treat a correct rejection as a successful open or a release failure.
3. For accepted files measure an export with one deterministic localized edit on a marked page; do not overwrite the input (recheck its hash). For page and form cases also follow the row-specific operation. For merge use an existing known clean fixture as the partner. Track no-download/blocked, failed save, or actual captured output bytes/hash separately. Reopen the captured bytes in the second reader; record open result and independently compare expected changed and untouched content (order, count, geometry, swatches/glyphs, annotations, field state or metadata as applicable). Use same-reader before/after comparison at fixed scale and configurable, recorded image tolerance; record unsupported checks as `unobservable`, not pass. Expect semantic preservation, not identical encoding, object numbering, exact xref style or preserved revision history. Report documented rebuild tradeoffs (such as form flattening) distinctly from corruption, regressions or unknowns.
4. Record monotonic elapsed milliseconds per trial: selection confirmation to first stable page display, selection to visible error when applicable, page navigation or zoom action to stable changed display, thumbnail availability after visibility, and download request to captured completed bytes (if actual completion is observable). Include early user interaction latency while the document is loading where observable, save and second-reader reopen timings, and process memory baseline/peak where a supported measurement exists (state method, units and process scope; otherwise unavailable). Define stable display by visible expected content at agreed scale and a repeatable observation rule, not by an internal parser event. For 50/500-page cases exercise first/middle/last navigation, return, edit/save/reopen; record page and operation timings separately by workload. Record raw trials and sample count, failures and censoring; summarize median and tail/range only with method and sample count. A watchdog limits the observation window and is logged; it is not a product timing criterion.
5. Evidence per run: corpus/manifest fingerprint, app revision, harness version/config, timestamp, browser/version/profile, OS/device/CPU/RAM, viewport/DPR, storage, power/network/cache state, oracle versions, repetitions, warmup/ordering, recorded watchdog and measurement clock. Keep local artifacts linked by case/trial ID. Record measurements for the environment actually exercised; emulation is not a physical device. Chromium, Firefox, WebKit, real iPhone and Android remain production coverage requirements, not claimed Phase 0 evidence. No numeric timing limits were supplied, so report measured values/environment without inventing pass limits.

**Original planning checklist (historical):** before execution, select an authorized CC0 affirmer, generator and second-reader versions, exact encryption profile settings, and reproducible run repetitions, tolerances, watchdog and device availability. Reconcile component metadata and low-visibility probes with chosen oracle capabilities.
