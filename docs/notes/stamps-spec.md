# Page stamps: layout and export, revision 1

Contributor: `work-6a745a79-017e-41b5-8d9b-2275929fc764` (page content stamp and numbering engineer), 2026-11-20. See the [independent runtime provenance review](../provenance/reviews/stamps.md) for integration results and limitations; this is not standing QA.

## Dialog and numbering

Open **Page tools → Add stamps** (on phones, open **Pages** first). The modal defaults to checked thumbnails, else all pages. The editable range is the only source of truth at Apply; it uses inclusive, 1-based current document positions, comma-separated with optional hyphen ranges. Duplicate and out-of-order entries are deduplicated and sorted in document order. Empty text fields are skipped. All enabled stamps share this range. Invalid ranges, labels, active numeric fields or geometry fail the entire preparation. Cancel or Escape before Apply commits nothing; both return focus to **Page tools**. The modal scrolls within the reduced phone visual viewport and does not add permanent chrome.

Numbering is opt-in by entering a format; e.g. `SEQ{n}-P{page}-T{total}`. `{n}` counts the chosen pages in document order, from the positive integer start (default 1); `{page}` is the current document position; `{total}` is the current page count, not the selection size. A format needs `{n}` or `{page}`; unsupported braces are rejected. Labels are frozen on Apply, including in derived PDFs and after reorder. Only Latin/WinAnsi characters accepted by the existing Helvetica encoding are supported.

## Geometry and history contract

`prepareStamps(pages, options, getPage, signal?)` returns `[{id, marks}]`, with stable workspace page IDs. `options` has `range`, `header`, `footer`, `format`, `start`, `watermark`, `opacity` (percent, 1–100), `angle` (degrees, −180 to 180), and `position` (`top`, `center`, `bottom`). `getPage(entry)` resolves the source PDF.js page for geometry only; blank entries must not acquire its content. The shared `entryView` incorporates effective source view or edited crop, UserUnit and both source/edit rotations. It describes the visible page, not the raw MediaBox. Use PDF.js's viewport inverse to convert the displayed baseline into unrotated PDF coordinates.

Header is upper-left, footer lower-left, numbers lower-right. The watermark is horizontally centered in its rotated metric rectangle at the selected vertical alignment. In the same batch it stays between the header and footer/number bands. The margin is the smaller of 24 points and 8% of either visible dimension. Labels use at most 12 points, watermark at most 48 points. Text shrinks to fit its region; a batch that needs any label below 1 point is rejected. A positive angle tilts up to the right from displayed horizontal. The renderer uses SVG with the same baseline, advance, angle and opacity as export. Pre-save SVG glyphs use the browser's Helvetica/Arial fallback, so raster shape/antialiasing need not be identical to a PDF reader. No live dialog preview or stamp thumbnail rendering. Existing content and separate stamp batches can overlap. Later page rotation/crop moves/clips stamps with the page rather than recomputing layout.

`{type:'stampBatch', edits}` is one immutable history entry. Only chosen entries get new mark arrays; every existing mark remains. Each item is `{kind:'stamp',stampId,role,text,x,y,size,advance,angle,opacity,color}`. `role` is `header`, `footer`, `number` or `watermark`; `x,y,size,advance` are unrotated PDF default user-space values, `angle` is native PDF angle, and `opacity` is 0–1. Appended stamps are content edits, not individually selectable annotations. Undo/Redo restores the exact prior/applied model. The same `writeMark` route writes `BT`/`Tj` operators and a PDF graphics state for opacity when materializing Save, drafts, split or extract. On reopen, stamps are ordinary PDF content, not imported marks. Recovery preserves content but not undo history.

## Reader and UI evidence for integration

Producer probe `/tmp/paperplane-stamps-proof.mjs`, log `/tmp/paperplane-stamps-proof.log`. Chromium desktop and WebKit touch emulation downloaded five-page PDFs before Apply, after Apply and after Undo. Range `4, 1-2, 4`, start `7`, format `SEQ{n}-P{page}-T{total}` produced 4 stamps each on pages 1, 2 and 4, including a cropped, non-zero-origin 90° page with UserUnit 2, a cropped 180° inserted blank and a differently sized 0° page. Pages 3 and 5 had unchanged extracted text, pixel checksum and decoded ops. Readbacks used PDF.js `getTextContent`/`render`, Poppler `pdftotext` per page and pdf-lib actual Contents streams and `ExtGState` `/ca`. PDF.js measured upright labels and 32° bottom watermark baselines; 2,949–3,208 gray-ink pixels across each engine's selected pages corroborated 35% opacity. Strict standalone validation, one-step Undo/Redo deep equality, six invalid-input controls, 12 AX role/name checks and 11 sequential focus/44px-size checks per engine passed. WebKit emulation retained the 390×576 stage on 390×664 and passed an offset/height visual viewport focus check. Native Chromium OPFS draft bytes reopened with the same content; the WebKit emulated context's `navigator.storage.getDirectory()` returned `UnknownError`, so native WebKit draft persistence was not confirmed. No device or full accessibility audit.

For independent tests use the production Save copy bytes, `#open-stamps`, `#stamp-range`, `#stamp-header`, `#stamp-footer`, `#stamp-format`, `#stamp-start`, `#stamp-watermark`, `#stamp-opacity`, `#stamp-angle`, `#stamp-position` and `#apply-stamps`. To measure orientation, transform the text origin and the end of its basis vector into the PDF.js viewport first; do not read `transform` as a screen-space angle or PDF.js `view` as raw MediaBox. Use pdf-lib `PDFPage.node.Contents()` and `decodePDFRawStream()` to inspect page operators, and resolve the referenced `gs` through that page's resources. The scratch driver is evidence only, not a shipped test or runtime hook.
